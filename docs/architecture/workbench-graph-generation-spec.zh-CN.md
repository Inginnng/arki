# 架构工作台：两种固定图形与高容错生成规范

状态：规范草案 0.2，2026-09-09。早期样式预览：`workbench-two-view-preview.html`；当前正式实现见 `../inline-reading-status.zh-CN.md` 的 0.2.6 节。

两种页面、独立场景步骤、同底图叠加、局部隔离与渲染回退已接入 0.2.6；完整候选保存等未实现项见末节。早期预览使用虚构的资料检索系统，不构成 AIMD 的源码分析结论；其中单条纵向流程已被正式版的同底图多场景阅读替代。

## 1. 固定两种页面，分开两类语义

| | 架构分析图 | 流程图 |
| --- | --- | --- |
| 回答的问题 | 系统由什么构成，各部分负责什么、归属哪里？ | 一次操作经过哪些步骤，数据如何处理和返回？ |
| 图中节点 | 有稳定身份的组件 | 有独立身份的操作步骤 |
| 基本形式 | 系统大框 → 子系统框 → 职责组件卡片 | 复用同一组件位置，按典型场景叠加转移、编号和高亮 |
| 重复规则 | 一个组件只有一个直接父级，在结构图出现一次 | 同一组件可负责多个步骤，可重复出现在流程中 |
| 连线规则 | 总览不铺满依赖线；选中组件后展开其接口与关系 | 箭头必须代表有依据的控制转移或数据传递 |
| 详情 | 输入、处理、输出、接口、代码依据 | 执行组件、输入、动作、输出、传递方式、代码依据 |

“固定”指图形语法、阅读方向、信息层级和降级方式固定，不是把所有项目塞入相同数量的方框。文档、证据、完整关系和诊断放在侧栏或抽屉；不增加第三种主图形页面。多个业务流程通过流程选择器切换，仍属于同一种页面。

架构图中的上下位置不能暗示运行顺序；目录名也不能直接证明运行边界。流程图不能由包依赖图自动改名得到。没有调用证据时可以展示架构，并明确“尚未确认操作流程”。

## 2. 固定视觉语法

### 架构分析图

- 系统和子系统用有标题的矩形容器，真正嵌套；外部组件必须画在系统边界之外，不能只靠文字声明“外部”。
- 组件卡片显示中文职责标题和一句摘要。代码标识、接口字段、完整解释与证据在详情展开。
- 顶层按边界排列，子层采用确定性的网格，不依靠连线排出归属。
- 默认展开约三层；更深层级通过折叠和展开继续阅读，不能删除层级或改写父级来适配画布。
- 没有可信归属的组件进入独立的“待归属”区。它是阅读辅助区域，不代表真实子系统。
- 选中组件后，详情列出入站、出站接口及数据。需要突出邻接关系时，只叠加选区相关的少量线，不改组件归属。

### 流程图

- 默认不再为步骤复制一套矩形。步骤在原组件上标注独立编号，在侧栏展开；分支、并行、合流和重试通过转移类型与条件说明。
- 切换场景只改变连线和高亮，不改变组件位置。纵向步骤图仅可作为未来局部展开方式，不是系统流程的统一约束。
- 步骤标题使用“动作 + 对象”，如“检索相关资料”，不是只写“服务端”。
- 箭头标签优先写实际数据，如 `question + scope`、`excerpts[]`。同步、异步、返回、重试有区别时必须保留。
- 返回数据可以记录在步骤 output 和调用详情中；只有确实存在独立返回处理步骤时才画成新步骤，不能为“闭环好看”虚构调用。
- 失败分支、并行、合流和重试必须有证据。只在默认模板无法表达时展开局部子流程，不能把并行假画成串行。
- 一个流程有明确入口与至少一个可确认结果；未读到的环节标为未确认，不能补造“成功结束”。

### 共同规则

正文采用可读字号，组件名默认最多两行。长文本先换行、增高；过长内容用短标题和详情索引收纳，全文仍能访问。容器跟随内容生长。信息过多时分组、折叠、分流程或允许正常滚动，不通过把全图无限缩小来满足首屏。

布局确定性：相同规范数据、模板版本和视口分类，得到相同的顺序。模型不决定坐标、尺寸、端口或路径。

## 3. 语义数据契约

生成分成三个独立层次：

1. **原始候选**：模型输出的有界结构数据。保留当前证据版本与生成诊断，不直接执行或插入页面。
2. **可呈现模型**：校验证据与引用、隔离有问题的记录后，形成可渲染的组件、边界、流程与待核对项。
3. **视图结果**：模板生成布局、交互图和导出。布局失败不能反向删除已经得到的语义内容。

建议字段：

| 数据项 | 关键字段 | 约束 |
| --- | --- | --- |
| `components[]` | `id, title, summary, parentId, input, processing, output, evidenceIds` | 描述组件职责。无可信父级用 null，不推断。 |
| `boundaries[]` | `id, title, parentId, evidenceIds` | 表达有证据的系统或子系统边界。归属不能成环。 |
| `relations[]` | `id, from, to, kind, payload, mechanism, evidenceIds` | 组件之间的接口、依赖或调用。导入只能证明依赖。 |
| `flows[]` | `id, title, trigger, entryStepId, steps, transitions` | 一条完整或明确标为不完整的操作流程。 |
| `steps[]` | `id, componentId, kind, title, input, processing, output, evidenceIds` | 步骤独立于组件身份；kind 为 action、decision、result 等受支持类型。 |
| `transitions[]` | `id, from, to, condition, payload, mechanism, evidenceIds` | from/to 指向步骤 ID；条件不确定时不得标为确认的分支。 |
| `unknowns[]` | `id, subjectId, question, reason` | 未确认内容是待查问题，不能伪装成已证实的图节点。 |

`evidenceIds` 只能来自本次服务端读取后签发的集合。有效编号只证明来源存在，不能自动证明它支持某项声明；还需检查声明与相关代码是否相符。对外 DTO 使用受控相对路径或不透明引用，不能泄露父任务 ID、绝对路径、原始运行日志。

模型只输出语义字段。颜色、坐标、SVG、HTML、CSS、布局引擎选项和通过回执都不属于模型输出契约。

### 流程节点与组件的最小示例

以下仅演示字段关系；`ev-1` 等是样例编号，真实生成必须绑定当前证据集合。

```json
{
  "components": [
    { "id": "browser", "title": "检索工作区" },
    { "id": "service", "title": "检索服务" }
  ],
  "flow": {
    "id": "query",
    "title": "一次资料检索",
    "entryStepId": "submit",
    "steps": [
      { "id": "submit", "componentId": "browser", "kind": "action", "title": "提交问题", "evidenceIds": ["ev-1"] },
      { "id": "search", "componentId": "service", "kind": "action", "title": "检索资料", "evidenceIds": ["ev-2"] },
      { "id": "show", "componentId": "browser", "kind": "result", "title": "展示结果", "evidenceIds": ["ev-3"] }
    ],
    "transitions": [
      { "id": "request", "from": "submit", "to": "search", "condition": null, "payload": "question + scope", "mechanism": "POST /query", "evidenceIds": ["ev-1", "ev-2"] },
      { "id": "response", "from": "search", "to": "show", "condition": null, "payload": "answer + citations[]", "mechanism": "HTTP response", "evidenceIds": ["ev-2", "ev-3"] }
    ]
  }
}
```

`browser` 在架构图中只出现一次，在流程中负责 `submit`、`show` 两个不同步骤。示例省略输入、处理、输出等详细字段，不是最终严格 JSON Schema。

## 4. 高容错分级

| 问题 | 处理 | 用户看到的状态 |
| --- | --- | --- |
| 空白、可缺省的展示字段 | 有确定含义才规范化；不修改事实字段 | 正常 |
| 标题长、标签挤、线路交叉 | 换行、增高、改标签位置；拥挤边用编号与完整关系列表对应 | 分析已保留，图形按需降级 |
| 单条关系端点不存在 | 隔离该关系，保留原文、对象 ID 和诊断；不补造节点 | 部分完成，1 条关系待核对 |
| 归属缺失或形成环 | 将受影响归属移入待核对区；保留有效组件及原关系 | 部分完成，部分组件待归属 |
| 重复 ID | 隔离冲突记录及依赖它的歧义引用；不能随机重命名后猜测连接 | 部分完成，身份冲突待修复 |
| 未知组件类型 | 用普通矩形作为展示回退，保留原类型和说明 | 内容不变，样式回退 |
| 流程存在孤立步骤或断点 | 主线展示可确认部分；其余放未连接步骤列表，不制造连接 | 流程不完整 |
| 缺少输入输出或调用证据 | 保留为待补充项；不能用“调用”“处理”冒充完整解释 | 待补证据 |
| 证据无效、来源变化、声明缺乏支持 | 撤下相应已确认标记；定位补读，保留旧版本及候选 | 待补证据 / 原证据已过期 |
| 布局算法异常 | 架构回退分组目录，流程回退步骤和分支列表 | 内容可读，图形暂不可用 |
| 输出无法解析 | 保留有界错误诊断及可安全保存的候选文本；只请求修复格式 | 生成未完成，旧版本可用 |
| 取消、越权访问或安全边界失败 | 停止相关动作；取消后的结果不自动应用 | 已取消 / 动作已阻止 |

高容错不等于“错误关系照画”，也不等于“任意原始输出都保存并公开”。隔离的项目保持可检查、可修复；有效内容无需跟着整批作废。候选仍按项目隔离、容量限制、敏感信息规则及用户取消意图处理。

数量上限分开两类：输入体积和计算资源保留硬上限；单页展示数量是软上限，可分页、折叠或拆分流程，不能静默丢弃超过数量的对象。具体硬上限根据实现预算确定，不在此设计草案中改动当前服务限额。

## 5. 保存、修复与状态

- 在证据版本绑定完成后，先保存安全的有界候选及诊断，再尝试布局。布局失败不消耗下一次模型调用。
- 已确认的旧版本与新候选分开保存；`partial` 不冒充完整版本，候选也不静默覆盖现有已确认分析。
- 内容状态建议为 `complete | partial | needs-evidence`；渲染状态建议为 `diagram | fallback`。二者独立。
- 定向修复只提供受影响对象、允许的证据与相关邻接结构。有效部分保持稳定，不为一条无效边重新分析整个项目。
- 同一问题无进展时先保留部分结果并改变修复方法，不无限请求模型重写。
- `complete` 表示选定分析范围内结构与证据检查完成，不表示已覆盖整个项目或已经人工认可模型准确率。
- HTML、Markdown 和图形导出都从同一份规范化数据生成；隔离项、未确认项和降级状态不能在导出时消失。

## 6. 确定性的回退顺序

架构：嵌套矩形 → 同级网格加折叠 → 分组目录。目录仍显示全部父级路径和组件详情。

流程：主线和分支图 → 单条流程及局部展开 → 有编号的步骤列表加明确的分支、合流与重试索引。列表中的顺序不得把未确认或并行操作解释成顺序执行。

标签：换行 → 调整间距 → 短显示标签加完整详情 → 编号对应完整关系。每一步保留原始标签及数据意义。

回退是模板内的确定性行为，不依赖模型再画一次。不伪造几何检查通过，不把回退视图说成完整图形通过验收。

## 7. 本轮预览与后续落地边界

预览已提供：两种固定模式、组件/步骤详情、浅深主题、长名称收纳、单条无效关系隔离的展示样例、布局不可用时的目录/列表样例。

早期预览使用固定示范坐标，仅用于设计讨论；当前正式版改用共享 ELK 组件布局与场景路由，支持多个流程选择及并行/合流关系。其余未实现项见本节最后一段。

0.2.6 实际字段采用 `nodes + groups + flows`；`flows.steps[].nodeId` 引用组件，`transitions.from/to` 引用步骤，模型候选使用 `evidenceIds`，保存的图转换为已核验的 `sources`。`issues` / `flowIssues` 表达待核对状态，尚未增加本草案提出的通用 `complete | partial | needs-evidence` 状态机。前文 JSON 是概念示例，当前接口以 `packages/contracts/src/architecture.ts` 为准。

正式版已实现同底图场景切换、逐步与分支阅读、并行/合流/重试标记、无效引用隔离、组件目录和传递列表回退、完整场景导出及旧存档兼容。尚未实现完整原始候选仓库、声明级证据支持审查、自动局部修复、自动折叠超大图和业务流程执行模拟。Archify 几何检查继续不参与工作台分析成功的前置条件。

## 同一架构底图上的典型流程（0.2.7；初版 0.2.6）

主画布固定为「架构分析图」和「流程图」。两种模式共享一份嵌套组件坐标，切换场景不重排组件；文档在独立弹窗中阅读。流程使用独立步骤 ID 引用组件，同一组件可参与多个步骤。支持条件分支、并行、合流、返回及有条件重试，目录编号不解释为串行执行；导航只沿已确认转移，分支由读者选择，不把导览当成业务执行器。

完整分析根据当前代码生成至多 5 个场景（通常 2–3 个，不能凑数）。每个场景有触发条件，步骤有输入、处理和输出，转移有条件、传输数据和机制，并分别绑定代码证据。旧 narrative 主线仅在旧存档阅读时转换为明确标记的兼容场景；依赖边不自动变成流程。提供 flows 的新分析不再生成或受限于旧版无环 narrative，正常请求—返回和重复参与不会因此触发整轮修复。

组件位置由 ELK 生成；流程路由避让固定组件与容器标题，重复方向的连接按组件对归并，双向传递有双向标记，编号对应完整传递列表。选区高亮当前组件及相邻传递；未参与组件淡化。没有可铺设的路径时保留传递列表；布局整体失败时保留组件目录及可继续选择的步骤。无效场景引用、缺失条件和重复身份按场景或记录隔离，显示待核对说明；源码变化仍阻止以过期证据继续分析。该机制不是声明级人工准确率验收，也未实现保留任意原始模型文本的完整候选仓库。

Markdown、文档弹窗和离线 HTML 同步保留全部场景、步骤、分支、重试与代码来源。HTML 为无脚本的可跳转静态导出，每个场景复用同一组件几何；布局失败仍可导出内容。现有 IndexedDB 存档兼容，重新分析成功后才替换旧版。旧记录可点击「分析典型流程」。

真实 Codex 公开合成计数服务验证：2 次模型调用、186866 ms，生成 3 个组件与「正常计算并缓存」「缓存命中返回」「非法请求拒绝」三个场景，共 15 步、12 条转移，三个场景均保留组件重复参与且无待核对项。首次尝试生成了有效场景，却被旧 narrative 的无环限制送入修复并超时；解除该兼容约束后复跑通过。未自动分析用户当前 AIMD 存档，不代表一般模型准确率或全项目流程覆盖。

## 历史：取消旧排版对分析的阻断（0.2.5）

修复 `ARCHIFY_COMPOSITION_AMBIGUOUS_CORRIDOR` / `ARCHIFY_COMPOSITION_LABEL_ROUTE_CLEARANCE` 导致已完成的 AI 分析被拒绝的问题。打开、完整分析、编辑和解释现在只返回经过证据与结构检查的图；React Flow + ELK 在浏览器内排版。旧 `rendering` 字段改为可选，兼容已有存档。工作台 HTML 导出也直接使用 ELK；只有显式调用旧兼容导出 API 才执行 Archify 及其原有回执检查。没有伪造通过回执，也没有放宽源码哈希、证据编号、对象引用、组件归属及取消检查。

因此，旧排版的线距、标签避让不能再阻断分析结果保存。若浏览器布局本身失败，架构文档和关系列表仍可阅读与提问。此前失败的模型提案未保存，更新后需要重新发起该操作。

验证：完整 `pnpm check` 通过 66 个测试文件、1026 项测试、类型检查及生产构建；18 项相关浏览器回归通过。注入上述两项旧排版错误后，初始打开、已存图打开、修改、解释及两阶段完整分析均不依赖旧渲染器；显式兼容导出仍按原规则报告错误。不带 `rendering` 的组件图通过选择、流程图、HTML 导出与刷新恢复测试，旧格式兼容测试也通过。0.2.5 已安装，42 个文件哈希与构建产物匹配；本地生产 API 实测成功返回 6 节点图且不含旧渲染字段。此轮未重跑真实模型，模型阅读与生成逻辑未改动。

## 历史：组件结构与运行流程（0.2.4）

工作台改用 React Flow（MIT）与 ELK.js（EPL-2.0，未修改第三方源码），许可证随自包含构建保留。组件结构采用可嵌套的子系统边界；运行流程只显示实现证据支持的调用与数据传递，静态依赖单独保留在完整关系列表。矩形、子系统与连线均可选择并追问。

完整分析分为定向阅读与架构综合：先按模块收集实现片段，由 AI 选择还需读取的调用方、接收处理器和契约；服务端在允许的文件清单中按符号/行号补读，再让 AI 独立组织组件与关系，不要求沿用包索引。最终至多 24 处代码片段、12 个组件、24 条关系、6 个子系统。组件归属需有证据且无环、无重复归属；每条确认的流程说明传输数据、调用方式、接收方处理和返回结果。证据编号在模型输出 schema 中限制为本次已读取集合。未读到的实现仍须明确保留为限制，不能据此声称覆盖全部项目。

旧存档不自动改写。尚无组件归属的分析显示「补充组件与数据流」；重新分析成功才替换当前版本。Markdown 与离线 HTML 导出同步包含组件归属及传输详情，HTML 中同时保留两个图。0.2.4 仍在分析后生成 Archify 兼容渲染，其九项回执仅代表兼容产物，不代表新画布已经过同一组几何检查；这一旧依赖已在 0.2.5 解除。

## 页面结构

本地网页 /web.html 提供两个独立工作台，入口为 apps/reader-ui/src/Workbench.tsx。

- **文档工作台**：按需加入项目 Markdown，或批量导入 UTF-8 编码、每个不超过 2 MB 的本地 Markdown。支持搜索、移除和恢复；移除不改变源文件。
- **架构工作台**：打开后直接扫描当前项目包声明、入口文件和代码导入，使用仓库内置的 Archify 生成可操作的 SVG。无需先添加文档或选择 Codex 任务。
- 点击矩形或连线，右侧显示其职责或关系以及代码来源。输入问题后，AI 默认可以协同完善选中部分及直接关联的模块和连线，也可以通过「允许 AI 修改的范围」选择整个架构图；在证据充分时增补连接到编辑区域的节点和关系。通过校验后自动更新画布。
- 支持缩放、拖动画布、适应画布、浅色/深色、撤销/重做和导出独立 Archify HTML；导出包含完整图、模块/关系说明卡片和来源位置。

## 保存与边界

文档列表、导入内容和架构版本分别存储于当前浏览器 IndexedDB，按服务提供的稳定项目摘要隔离。架构最多保存 20 个版本；撤销后继续修改会替换后续分支。切换工作台保留当前图和问题结果，刷新恢复图、修改历史和最近 20 次完成的架构问答；未完成的请求不会自动重发。

保存的架构会重新检查证据哈希。项目代码变化时，旧图可以查看和导出，重新生成后才能继续提问。生成、问答、撤销和导出都不会修改项目源文件。旧架构资料列表的数据保留在原存储中，新图形界面不再使用它。

文档划词问答继续通过 /api/side 使用显式选择的任务片段。架构编辑独立使用 /api/architecture，只使用当前项目证据，不宣称继承桌面当前任务。外部导入文档仅用于本地阅读，不作为当前项目证据。

## 架构编辑契约

初次进入架构工作台会执行一次架构解读；旧存档不会自动重放模型请求，可用「解读模块与流程」或「重新生成」重新分析。重新分析成功前保留旧版本。初始图明确标记为草图，是有界的代码依赖概览，不将代码导入直接解释为运行时调用。当前上限为 12 个节点、24 条关系；一次 AI 修改最多增加 3 个节点和 4 条关系。扫描不覆盖整个代码库，无法确认的内容应显示为限制。

AI 读取按模块分配的实现片段（最多 24 处），而非仅包声明或导出入口。职责使用简短的中文标题，原代码名为辅助标识；关系区分静态依赖与有实现依据的调用/数据传递。整图解读可返回有代码证据的连续阅读主线，同步显示在图和文档中。

模型只返回受 Zod 约束的数据，不能提供 HTML/SVG、源路径或任意写入指令。服务核验用户选择的编辑范围、稳定 ID、已签发证据引用、新增部分的连接性及调用前后的文件哈希。现有对象支持批量更新；AI 回传的未改动内容会忽略，不因超出关联范围而误拒绝。只有实际 Archify 渲染并通过检查后才返回新图；无效修改或取消保留旧图。引用与哈希校验不等于独立语义审核。

Archify 运行时内置在 third_party/archify，不依赖个人 skill 目录，也不在运行时下载品牌资源。使用 showcase 质量配置和真实 deliver 校验流程，9 项检查、零错误和零警告后才交付。总览按有证据的主线与支路组织，并用有意义的标签说明方向；其余关系保留在完整关系列表及导出文档中。嵌入图在隔离 iframe 中运行，消息需要匹配 iframe 来源、随机通道和图中的有效 ID。独立导出保留 Archify 查看器。

AI 修改未通过格式、范围或证据引用校验时，服务会把具体问题反馈给模型，最多自动修正一次。修正仍失败时保留原图并显示诊断；不反复重试，也不放宽代码证据校验。

错误反馈分为请求、证据、模型、修改校验和图形渲染阶段。页面显示具体原因与处理建议，展开后可查看对象 ID、字段、实际值、允许值和请求编号，并复制诊断。服务日志以相同请求编号记录这些安全诊断；不记录问题正文、完整模型输出、堆栈或绝对本地路径。

## Markdown 问答连接与诊断

本地网页启动时，如果没有 HTTP_PROXY、HTTPS_PROXY 或 ALL_PROXY（含小写）显式配置，则读取已启用的 Windows 手动系统代理，只注入当前后台进程的环境，并让 localhost、127.0.0.1 和 ::1 绕过代理。已有显式代理优先；不会修改 Windows 设置或用户 Codex 配置。PAC 和仅 SOCKS 配置不自动转换。代理设置改变后需要重启网页后台。

本次超时排查复现：上下文和代码证据约 2.5 秒准备完成，随后模型连接失败并连续重试，最终触发 120 秒问答时限。后台没有代理环境变量，而系统浏览器使用已启用的本机代理。只为诊断进程接入现有代理后，不含项目内容的算术问题在同一模型及思考强度下约 12 秒返回。修复保留原时限及模型配置。随后使用临时生成的公开 MCP 文档、代码片段与讨论，完整执行 HTTP 接口、选区取证、真实模型调用和引用校验，约 39 秒返回有效答案。此验证不使用用户项目内容。

Markdown 错误现在包含失败阶段、运行耗时、连接重试次数、最近模型错误分类和请求编号，可复制诊断。服务日志记录同一份安全诊断；不包含任务标识、绝对路径、问题正文或原始模型错误文本。失败后保留问题和选区，允许重新提交。

## 故障恢复与存储降级

本地 Markdown 运行时初始化失败、连接中断或临时模型会话清理失败后，下一次操作会重新建立连接。已选择的讨论快照保持原截止点和有效期，恢复后仍会重新核对来源任务所属项目。不会自动重放失败的模型请求。任务列表和历史分页接受取消信号，取消后停止后续读取。

Markdown 接口整体等待上限为 180 秒，架构接口为 240 秒；底层不及时响应取消时，接口仍会结束等待并返回安全诊断。Markdown 模型阶段原有 120 秒上限保持不变。本地 HTTP 服务还限制请求头和请求体接收时间。启动端口冲突时清理已创建的服务；退出时先停止运行时，同时关闭 HTTP 服务，最多给现有 HTTP 连接 5 秒收尾。

浏览器数据库打开与事务等待均有 5 秒上限。读取结果先验证格式，错误通过 Promise 正常返回；数据库升级受其他标签页阻塞时不会无限等待。只有事务提交完成后才标记已保存。架构恢复失败时保留原存档、展示从当前项目生成的内存版本；保存空间不足时保留本次图和撤销历史，并明确提示尚未保存、可导出。文档收藏结构异常时显示存储错误，不把异常对象交给页面渲染。

这些恢复机制不保证外部模型服务始终可用；需要用户重新提交的问题会保留在页面上。
